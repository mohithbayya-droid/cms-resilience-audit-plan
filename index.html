1. Background & Context

On Oct 16, the Plans & Pricing page returned 500 errors for en-GB and en-IE storefronts. The cause: a Contentful II18Next entry referenced by an addon's cost field was not published for those locales. With removeUnresolved: true set, the SDK silently removed that link — leaving undefined where code expected an entry, which crashed the SSR render and returned a 500 to every visitor on those locales.

⚠
Root cause: missing null guards at the transformation layer

removeUnresolved: true strips unresolved link objects from the response, but it does not add null guards to any access point downstream. Every required linked field typed as non-optional in the content types (seo, trialTermsUrl, privacyUrl, addon cost, …) is a latent crash site whenever that entry is unpublished for a locale.

This work is split into two parts:

Part 1 — this document Architecture Audit

Map every CMS entry point, content type, fetch path, and transformation layer. Identify all crash-risk access patterns across all widgets and pages so the solution covers everything, not just addons.

Part 2 — after audit Solution Design & Implementation

Based on audit findings. Sync with Meghana and Tim on CSF and subscriptions-billing (migrated or in progress). Decide whether the fix belongs at the fetch boundary, the transformation layer, or per-widget.

3. The removeUnresolved: true Gap

All three Contentful clients set removeUnresolved: true. The intention was to handle missing entries, and many engineers assumed this makes the codebase resilient to unpublished content. It doesn't.

What it does

  • Array fields: removes unresolved entries from the array (silently, no error)
  • Object/reference fields: sets the field value to undefined

What it doesn't do

  • Does not add null guards to any code that reads those fields
  • TypeScript typed fields stay typed as II18Next, IHyperlink, etc. — the compiler gives no warning
  • Any access like entry.fields.cost.fields.key still throws TypeError at runtime when cost is undefined
🔎
The Oct 16 failure chain

Contentful entry 577ZOq7Skw9OSTkGxbPlPX (an II18Next addon cost item) was not published for en-GB / en-IE. → SDK sets addon.fields.cost = undefined. → mapAddonEntryToProps() spreads ...addon.fields — this is safe, no crash here, but cost: undefined is now in the mapped output. → A component in the pricing-plans widget renders addon.cost.fields.key without a null check. → TypeError: Cannot read properties of undefined → Next.js SSR catches the render crash → HTTP 500.

The getStaticProps wraps everything in a try/catch that re-throws (by design — prevents the ISR cache from updating with broken data). For ISR with fallback: 'blocking', the first request for a locale like en-GB has no cached response to serve. Every visitor on that locale sees the 500 until a content editor publishes the missing entry.

Pattern B — Unresolved field spreads as undefined, crashes in component tree

The Oct 16 incident. mapAddonEntryToProps() itself is safe — it spreads ...addon.fields which harmlessly includes cost: undefined. The crash happens downstream when the component tries to render cost.fields without guarding against it being undefined.

📍
Exact crash location confirmed — widgets/pricing-plans/src/components/Addons/_Card.tsx, lines 64–65

addonData?.cost uses ?. only to guard against addonData being null — it does not protect against cost itself being undefined. When the cost II18Next entry is unpublished for a locale, addonData.cost is undefined and .fields throws. 

// services/cms/utils.ts — mapAddonEntryToProps — safe, cost: undefined just spreads harmlessly
return group?.fields.addons.map((addon) => ({
    ...addon.fields,    // cost: undefined is in here — no crash yet
    json: addon.fields.json ? ...
}));

// widgets/pricing-plans/src/components/Addons/_Card.tsx:64 — ACTUAL CRASH ↓
return t(addonData?.cost.fields.key as string, {     // ← TypeError here
    defaultValue: addonData?.cost.fields.value,      // ← and here
});

// Fix — add ?. after cost
return t(addonData?.cost?.fields?.key as string, {
    defaultValue: addonData?.cost?.fields?.value,
});
📋
subscriptions-billing component tree still needs a search pass

The pricing-plans crash site is confirmed above. widgets/subscriptions-billing/src/ still needs a grep pass for the same unguarded .fields pattern on fields that removeUnresolved could nullify.

Pattern C — Cancel-Save Flow Already safe

CSF does not call Contentful at render time. The migrated widget at plg-cancel-save-flow/src/ loads CMS data from pre-generated JSON files bundled at build time (src/generated/{locale}/cancelSaveFlow.cms.json). If a locale's JSON is missing it automatically falls back to English — see src/store/sagas/cms.sagas.ts lines 46–58. There is no live Contentful SDK call, no removeUnresolved risk, and no crash surface from this pattern. No action needed for CSF.

7. Open Questions for Full Audit

  1. Which Contentful fields are genuinely optional at the data model level for non-US locales? The TypeScript types from @dxp/content mark some fields as required, but Contentful's own content model may not enforce this per-locale. We need to understand which fields are required by contract vs. optional by practice before designing the fix.
  2. Is the crash always in SSR, or also in client re-renders? The Oct 16 crash was SSR (500). But client-rendered widgets that receive CMS data as hydration props may also crash on client re-render if the undefined field reaches a component that doesn't guard it. Need to verify whether the fix needs to cover both SSR and client execution paths.
  3. How should ISR interact with partially-missing CMS content? The current catch-and-rethrow prevents a broken ISR cache update, which is correct. But a better outcome is the page rendering in a degraded state (no addon section, for example) rather than 500ing — because then the ISR cache gets populated and subsequent requests are served the degraded page instead of hitting the origin again.
  4. Where should the fix live — fetch boundary, transformation layer, or component? Three options: (a) post-fetch validation that strips/flags invalid entries; (b) optional chaining throughout all mappers; (c) null guards in component render. Otilia's guidance points toward option (a) or (b) — "at the boundary where Contentful data enters the app." The full audit scope will clarify which is most tractable given the dual-client architecture and CSF migration.
  5. Should there be a shared Contentful error boundary or data-validation utility? If the fix is systemic, it should be a single utility that all fetch paths go through, not per-mapper patches. The apps/commerce-web/src/services/cms/ layer is a good candidate for the insertion point — but only after the subscriptions-billing divergence is resolved.
